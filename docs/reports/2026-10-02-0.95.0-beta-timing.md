计时口径：端到端时间按实际墙钟计算；并行 job 的耗时不相加充当用户等待时间。GitHub job 的 `created_at → started_at` 作为可观测的近似调度/排队时间，`started_at → completed_at` 作为 job 时间；step 时间用于区分安装、构建、验收、签名和上传。job 创建前的依赖等待另算，不能归到 runner 排队。API 时间戳精度为秒，host step 与 job 边界偶有秒级差异；workflow 墙钟统一取创建到最后一个 job 完成，而非 metadata `updated_at`。签名/公证若共处一个 step，当前只能报告组合时间，不能臆测其中每一部分。起点到首轮结束之间的数据收集、轮询、并行报告编写和本地操作均计入墙钟，但不冒充构建时间；18:28:37 后的账号等待和报告整理需续写，不能混入已结束首轮的时长。

基于当前证据的优化方向（收益待对照测量）：

1. 把会在昂贵 native 步骤末尾才暴露的固定前置条件放进快速 preflight，例如独立验收脚本的包导出是否能加载、测试退出动作是否仍符合产品行为。保留完整 native 验收，用早失败减少整轮返工。
2. 研究 dev CLI 对完整 Broker Pack matrix 的串行依赖。每个 native CLI 只消费自己平台的 Pack，但现在要等全平台最慢项；可以试验按平台连接候选构建，最后激活仍等待完整六平台和全部合同。先拿三次同源对照记录证明收益，不能直接把等待时间当成可节省时间。
3. 先检查 Windows ARM64 的 setup-node 缓存、依赖安装、Broker Pack 构建/compiled 验收。已观察到排队约四秒，当前证据不足以支持“买更大 runner 就会快”。缓存只允许复用安全输入，最终候选包验收照跑。
4. 区分操作耗时和流水线耗时：本次完整测试与构建误重叠、安装器 fixture 状态误用，以及诊断/记录工作也造成等待。修正执行顺序和使用干净 fixture，比减少验证覆盖更直接。
5. 研究公证账户的快速健康检查：验证只读探测能否提前识别协议 403，而不是只验证密钥可用；若做不到，发版前由 Account Holder 确认账户协议。缺陷和延期理由已记录在 [#1754](https://github.com/TraderAlice/OpenAlice/issues/1754)。最终公证、签名和候选验收仍保留。这次成功公证时间尚不存在，不能用失败步骤推断 Apple 通常要多久。

本次只修复阻塞发版的门禁，不实施上述流水线优化。数据来自同一次发版及一个已完成的参考 run，缓存、网络和平台状态并未控制；没有前后对照实验，不能把第三次更快直接归因到优化。
