# Workspace Template Upgrade

This guide owns in-place reconciliation of launcher-managed template assets in
a durable Workspace: three-way planning, reviewed apply, transaction recovery,
and the checkout boundary shared with [[docs/workspace-absorb.md]].

Template Upgrade is not bootstrap and never replaces the Workspace directory.
Only templates declaring `"upgradeStrategy": "managed-context"` participate.
Source-pinned Harnesses use their exact-commit Git workflow instead.

## Managed scope

The managed set is limited to template README/instructions, template-owned
`.agents/skills/**` and `.claude/skills/**`, and legacy `.pi/skills/**` duplicate
reconciliation. Alice Harness companion Skills are independently owned by
[[docs/alice-harness.md]] and excluded from template plans.

Research, reports, Issues, Inbox records, credentials, runtime state, Git
history, and every other Workspace file are never candidates. A template
upgrade must not silently rewrite user work or the complete repository.

## Three-way plan

Every plan compares exact snapshots:

```text
Base      last managed template snapshot applied to this Workspace
Local     managed files in the live Workspace
Incoming  managed files generated by the current template
```

Fingerprints, not timestamps, classify changes:

- Incoming-only changes are ready to apply.
- Local-only changes are preserved.
- Non-overlapping dual text edits use Git three-way merge.
- Overlapping or incompatible add/delete edits require explicit resolution.
- Identical Local/Incoming files do nothing.

The preview digest covers Base, Local, Incoming, template identity, and both
versions. Apply must present that exact digest and materialize Incoming once
for the attempt. A Local or template change after preview invalidates the plan;
apply never substitutes newly published content for reviewed content.

Regular dual-edited text uses `git merge-file --diff3` against Base. Conflict
markers are never written automatically. Operational Git failure aborts preview
rather than masquerading as a content conflict. The next recorded Base is the
official Incoming snapshot, so preserved user edits remain local changes on
subsequent upgrades.

## Baseline and versions

New Workspaces record state and compressed Base under
`.alice/template-upgrade/` after the root commit; `.git/info/exclude` keeps this
secret-free bookkeeping out of Git. Legacy Workspaces reconstruct Base from the
root commit on first preview without startup rewrites. Thereafter recorded Base
is authoritative; editing README frontmatter does not complete an upgrade.

Discovery and apply use shared SemVer precedence. Lower candidates are blocked;
missing/malformed versions are unknown, not zero. Changed Incoming at equal
precedence requires a version bump. Apply rechecks under the lease. Alice
Harness content reconciliation is independent and may apply same-version edits.

## Apply transaction and recovery

Apply takes the shared per-Workspace checkout-operation lease. Offboarding and
Absorb use the same guard; Absorb holds source and target leases in order.
Template apply refuses active interactive/Web/headless Sessions and a staged Git
index so it cannot absorb unrelated changes or rewrite live instructions.

The transaction:

1. Re-plan against one Incoming snapshot and validate the reviewed digest.
2. Validate every conflict choice.
3. Write journal plus Before/Incoming snapshots under
   `.alice/template-upgrade/transaction/`.
4. Atomically replace/remove only selected managed paths.
5. Stage only those paths and create an isolated template upgrade commit.
6. Persist Incoming as Base and remove the transaction directory.

Pre-commit failure restores every touched path and resets only those index
paths. If commit completed before interruption, startup recognizes its trailer,
finalizes Base, and removes the journal. Recovery runs before scheduled work so
Agents never start against half-applied instructions.

[[docs/update-lifecycle.md]] may compose this operation with other owners, but
digest, activity, conflict, and lease checks remain authoritative. Shared Git
receipts and committed trailers prove completion after a lost response; the
coordinator never resolves conflicts or changes the approved target.

## Agent and UI boundary

Workspace Settings → Template and `alice template upgrade` expose the same
read-only preview and reviewed apply. Conflicts require explicit per-path
choices. A live Session cannot upgrade its own instructions; pause it or use a
separate Manager. Headless runs may preview a peer but cannot apply it.

The updater never dispatches an Agent to resolve conflicts. AI-assisted edits
return through a refreshed plan and explicit acceptance. Template Upgrade uses
Base = previous template; Absorb copies user assets between Workspaces. They
share plans, leases, journals, and audit commits but remain distinct operations.

## Load-bearing paths and verification

- `src/workspaces/template-upgrade.ts` — snapshots, planning, transaction, recovery.
- `src/workspaces/workspace-operation-guard.ts` — shared checkout serialization.
- `src/workspaces/template-registry.ts` — explicit managed-context opt-in.
- `src/workspaces/workspace-creator.ts` — exact creation baseline.
- `src/workspaces/service.ts` — composition, activity gate, recovery ordering.
- `src/webui/routes/workspaces.ts` and
  `ui/src/components/workspace/WorkspaceTemplateUpgradePanel.tsx` — preview,
  conflict decisions, and apply.
- `tests/integration/workspace-upgrades/template-upgrade.spec.ts` — plan, stale
  digest, concurrency, rollback, baseline, and real-template coverage.

Changed behavior requires this integration coverage, owning typechecks, and the
real UI or CLI path. Exercise rollback or committed-transaction recovery when
journal ordering changes. Apply [[docs/development-workflow.md]] for shared
checkout/update-lifecycle acceptance.
